> 「程序员转行机器人数据」系列第二篇。[上一篇](/2026/11/12/robot-data-collection-methods/)讲了五种采集方式。这一篇换个角度：**一条刚采回来的原始数据，要经过什么才能变成模型真正能用的训练数据？**
>
> 结论先放前面：采集设备决定数据的上限，数据工程决定数据能不能用。而后者，恰好是程序员最熟悉的领域。

## 一、原始数据长什么样

假设一个双臂工位在做“把零件放进料盒”，一次操作会同时产生这些信号：

| 信号 | 典型频率 | 说明 |
|---|---|---|
| RGB 相机（头部 + 双腕） | 30 Hz | 3 路视频 |
| 深度相机 | 15–30 Hz | |
| 关节位置 / 速度 / 力矩 | 200–1000 Hz | 每臂 6–7 个关节 |
| 六维力传感器 | 500–1000 Hz | 末端 Fx Fy Fz Mx My Mz |
| 触觉传感器 | 100–500 Hz | 阵列数据 |
| 夹爪开合 | 100 Hz | |
| 控制指令 / 遥操作输入 | 100–500 Hz | 这才是 action |
| 语音 / 任务指令 | 事件型 | |

十几路信号、频率差几十倍、来自不同厂商的设备、各自有各自的时钟。

小样本时，这些问题靠人工挑一挑还能凑合。数据量一旦到了上万条，错位、丢帧、漂移、标签不一致会成批出现，**数据治理的成本很容易超过采集本身**。所以需要的不是“更勤快的标注员”，而是一条流水线。

我把它拆成五关。

## 二、第一关：时间同步

### 为什么这是头号问题

一个程序员很熟悉的类比：**分布式系统里没有统一时钟，日志就没法排序**。

机器人数据也一样。如果相机时间戳和力传感器时间戳差了 30ms，模型看到的就是“手还没碰到杯子，力已经上来了”。它学到的是错误的因果，而不是真实的物理交互。这种错误很隐蔽：训练能跑，loss 也会降，只是上真机就是不灵。

### 硬件同步优先，软件对齐兜底

**源头解决**：让所有设备共享同一个时钟。常用的是 IEEE 1588 PTP（精确时间协议），配合硬件触发让相机曝光对齐，每个采样点都打上全局绝对时间戳。

**软件兜底**：即使有了统一时钟，不同频率的信号仍然要重采样到同一个时间轴上，通常以相机帧为基准。规则很简单：

- **离散信号**（夹爪开 / 合、按钮事件）：取时间上最近的一个采样；
- **连续信号**（关节角、力）：在前后两个采样之间插值；
- **必须设置容差**：比如超过 5ms 就找不到匹配，就标记为缺失。**宁可丢，也不要错配**。

还有一个容易忽略的细节：纳秒级时间戳直接转成浮点数会丢精度，插值前要先减去起始时间。

对齐之后，建议把**每一路的对齐误差分布**写进这条数据的质检报告。后面排查“为什么这批数据训不好”时，这是第一个要看的指标。

## 三、第二关：切分与脏数据剔除

不管是人类示范还是遥操作，原始录制里都有大量无效片段：试探、犹豫、空抓、碰撞、视野被挡、操作员走神。按行业从业者的经验，这类数据的占比往往能到三成。

靠人工看视频挑，问题有两个：慢，而且每个人的标准不一样，这批和那批的质量没法比。

更可靠的做法是**视觉和力觉双模态判别，并且把规则写死在代码里**：

- **力觉 / 夹爪信号**：判断“什么时候真正接触、什么时候真正抓住”，物理阈值很客观；
- **视觉信号**：判断“抓的是不是目标物体”“有没有遮挡”“任务最后是否完成”。

以力觉部分为例，最朴素的切分逻辑是：

1. 当合力超过某个阈值，或夹爪闭合到一定程度，判定为“接触中”；
2. 找出所有连续的“接触中”区间；
3. 太短的（比如不到 0.5 秒，多半是误碰）和太长的（比如超过 20 秒，多半是卡住了）都丢进异常区。

实际工程中，还要在每个片段前后各留一段“接近”和“撤离”的过程（模型需要学会怎么靠近物体），并把被剔除的片段**归档而不是删除**：失败数据本身也是宝贵的训练和评测素材。

关键不在于阈值取多少，而在于**规则固化、版本化**。这样每一批数据都按同一把尺子量，才能累加、对比、稳定迭代。

## 四、第三关：动作与语言对齐

现在的主流模型（VLA，视觉-语言-动作模型）需要“这段动作对应哪句指令”。

常见的做法是**事后人工配文**：采完了，标注员看视频写描述。问题是时间边界粗糙，描述口径五花八门（“拿起杯子”“抓取水杯”“pick cup”），数据只能在单个项目里自用。

更好的做法是**前置标准化**：

1. 采集前先定义**原子动作词表**（如 `reach / grasp / lift / move / insert / place / release`），并为每个任务配好标准指令模板；
2. 采集时由系统提示当前步骤，操作员按步骤执行；
3. 后处理时用时序特征（速度、夹爪状态、接触力）自动匹配动作边界，再由人工抽检。

产出的结构大致如下：

```json
{
  "episode_id": "ep_20261112_000123",
  "task": "把蓝色零件放进左侧料盒",
  "segments": [
    {"skill": "reach",   "start_frame": 0,   "end_frame": 42},
    {"skill": "grasp",   "start_frame": 42,  "end_frame": 61},
    {"skill": "move",    "start_frame": 61,  "end_frame": 130},
    {"skill": "place",   "start_frame": 130, "end_frame": 151},
    {"skill": "release", "start_frame": 151, "end_frame": 160}
  ]
}
```

这就像给代码定义接口：**词表统一了，数据才能跨项目复用**。

## 五、第四关：选一个数据格式

自研格式最容易踩的坑是：换个团队、换个模型就读不懂。所以尽量站到社区标准上。目前最常见的两个是：

**RLDS**：Google 推出，[Open X-Embodiment](https://github.com/google-deepmind/open_x_embodiment) 汇集了多家实验室、22 种机器人本体的数据，用的就是它。结构是 `dataset → episode → step`，每个 step 包含 `observation`、`action`、`is_first`、`is_last` 等字段，基于 TensorFlow Datasets。

**LeRobotDataset**：Hugging Face [LeRobot](https://huggingface.co/docs/lerobot/lerobot-dataset-v3) 的格式，PyTorch 生态。v3.0 的设计很“工程化”：

```text
my_dataset/
├── meta/
│   ├── info.json        # schema：字段名、dtype、shape、fps
│   ├── stats.json       # 归一化用的均值/方差/最值
│   ├── tasks.parquet    # 自然语言任务 → 整数 ID
│   └── episodes/        # 每条 episode 的长度、任务、偏移量
├── data/                # 状态、动作、时间戳 → Parquet（多 episode 合并成大文件）
└── videos/              # 每路相机 → MP4 分片
```

数值数据用 Parquet，图像用 MP4 视频编码，episode 的边界靠元数据里的偏移量定位，不靠文件名。这样做文件数少、加载快，还支持从 Hub 流式读取。

怎么选？**训练栈用什么就交付什么**。两者之间有转换工具，但最好在源头就做对。

### 一个隐蔽的坑：observation 和 action 错一位

在 RLDS 的约定里，第 t 步表示“看到 `o_t` 之后执行了 `a_t`”。如果打包时把 action 和 observation 错开了一帧，训练照样能跑，模型却在学“已经发生的动作”。

一个简单的自检思路：**动作应该领先于状态变化**。把动作序列前后平移几帧，分别算它和“下一时刻状态变化量”的相关性。正常情况下，相关性最高的位置应该在 0 或很小的正偏移处（对应控制延迟）。如果峰值出现在负偏移处，说明动作反而落后于状态，打包时大概率错位了。

这个检查适用于“动作是目标位置增量或速度”的场景；动作定义不同时，思路一样，判据要相应调整。把它放进类似 CI 的入库检查里，能挡掉一大类“训练不报错但效果奇差”的问题。

## 六、第五关：可追溯与版本管理

“数据资产”和“一次性素材”的区别，在于**出了问题能不能查到根**。

模型在某个场景上翻车了，你需要回答：用的是哪批数据？哪台设备、哪次标定、哪个场景配置？经过了哪个版本的清洗规则？

一个可行的做法是给每条 episode 生成一个**指纹**：原始文件内容加上标定参数，再加上流水线版本，三者一起算哈希。任何一项变化，指纹都会变。这和 Git 用内容哈希标识提交是同一个思路。

配套的元数据，建议至少覆盖四个维度：

```yaml
fingerprint: 3f9a1c0d7b2e4a61
hardware:            # 硬件与标定
  robot: dual_arm_v2
  cameras: [head_rgb, wrist_left, wrist_right]
  calibration_id: calib_20261110_03
scene:               # 场景与环境
  site: lab_a
  lighting: warm_500lux
  objects: [blue_part_m6, tray_left]
physics:             # 物理交互特征
  max_force_n: 18.2
  contact_frames: 96
annotation:          # 训练标注
  task_id: 17
  skill_vocab_version: v3
  pipeline_version: clean-2.4.1
```

有了这些，就能像查数据库一样，按场景、材质、动作类型**抽取训练子集**；也能做一个**数据质量看板**：哪个场景的失败率高，哪类动作样本不足。看板反过来决定下一轮该采什么，形成闭环。

如果你用过 DVC、Delta Lake 或者 LakeFS，会发现思路完全一样：快照、增量、可回滚。

## 七、比流水线更重要的：先想清楚为什么采

流水线解决的是“采得对”，但还有一个更前置的问题：“该不该采”。

和几位从业者交流后，我把验收一批数据的标准归纳成三个问题：

1. **需求是真的吗？** 有没有明确的场景方、明确的任务定义和验收标准（物料状态、节拍、允许误差、异常怎么恢复）？先大量采“抓取、搬运”，以后再找用途，大概率是做无用功。
2. **模型用得上吗？** 相机视角、起始位姿、速度分布、格式和时间戳是否符合训练方的要求？该统一的有没有统一，该覆盖的变化有没有计划地覆盖？
3. **下次还能复用吗？** 做完第一个项目后，第二个同类项目能不能少采一点、少调一点、更快交付？能复用的往往不是某条具体轨迹，而是任务拆解、采集规范、评测方法和适配经验。

完整的闭环是这样的：

1. **场景需求**：明确任务和验收标准；
2. **采集规范**：确定设备、视角和动作词表；
3. **采集**：按规范录制原始数据；
4. **流水线**：完成同步、切分、对齐和打包；
5. **训练**：用标准数据集训练模型；
6. **真机评测**：在真实机器人上验证效果；
7. **定向补采**：根据失败模式补充数据，再回到采集；
8. **沉淀资产**：把规范、工具和技能库反馈到下一轮采集规范。

**数据产能本身不是护城河。能把这个圈转起来、并且越转越快，才是。**

## 八、程序员能在这里做什么

回到这个系列的初衷。如果你也是程序员，想进入机器人数据领域，可以从下面这些方向切入：

| 方向 | 需要的能力 | 你可能已经会的 |
|---|---|---|
| 采集端软件 | 设备驱动、ROS 2、时间同步、高吞吐写盘 | 系统编程、网络、并发 |
| 数据流水线 | 批处理 / 流处理、质检规则、格式转换 | ETL、Airflow、Spark |
| 数据平台 | 存储、索引、版本、检索、看板 | 后端、数据库、数据湖 |
| 标注与回放工具 | 多路视频同步回放、时间轴标注 | 前端、可视化 |
| 评测框架 | 自动化测试、统计分析、失败归因 | 测试开发、CI |
| 仿真工程 | 场景搭建、域随机化 | 游戏引擎、3D |

我的学习路线建议：

1. 跑一遍 [LeRobot](https://github.com/huggingface/lerobot)：下载一个公开数据集，看懂它的 schema，跑一次训练；
2. 读 [UMI](https://umi-gripper.github.io/) 的代码：它的 SLAM 流水线、数据过滤和导出逻辑，就是一个完整的“采到能训”的样板；
3. 学一点 ROS 2 和坐标变换（tf），理解机器人数据里的“位姿”到底是什么；
4. 动手做一个小工具：比如把两路不同频率的传感器数据对齐，再导出成 LeRobot 格式。

机器人数据这个领域还很早期：路线没收敛，标准没统一，工具链到处是空白。对算法研究员来说，这是不确定性；**对工程师来说，这是机会**。
